# Agent guide

This repository contains a small Windows WinForms utility with optional WSL Codex integration. Keep changes focused and dependency-free unless a new dependency is clearly necessary.

## Architecture

- `UsageIndicatorForm` owns widget lifecycle, polling and interaction; `WidgetFace` draws it. `AccountManagerForm` contains the Codex and Claude account surfaces.
- `CodexDesktopStateReader` detects the packaged Codex Desktop host. `AppServerClient` runs the local official `codex app-server --stdio` and speaks JSONL. Codex weekly usage is the returned window closest to seven days.
- `CodexAccountStore` owns the encrypted Windows login vault and recovery; isolated account queries are separate from active widget polling and the manager's combined observation set.
- `ClaudeAccountController` binds verified profile identity and widget usage. `ClaudeProfileStore` holds non-secret metadata; `ClaudeProfileRuntime` invokes the unmodified official CLI for sign-in, identity checks and usage only.
- `ClaudeShelfService` (owned by the widget) observes the packaged Claude Desktop app off the UI thread. `ClaudeDesktopProbe` reports run state, the installed package and the compatibility guard; `ClaudeDesktopLogWatcher` follows the app's own log for the current run's account. `ClaudeSessionShelf` fills other accounts' Code session lists ("shelves"); `ClaudeShelfAccounts` maps profiles to account/organization pairs; `ClaudeAppFollower` keeps the widget's usage selection on the app's confirmed account.
- `ClaudeCodeUsageSource` parses official `/usage` output. `ClaudeUsageClient` owns the shared request throttle, caching and backoff; `ClaudeDisplayMetric` selects overall or Fable weekly without issuing a query.
- `WslCodexBridge` probes and operates supported Linux targets. `WslCodexService` owns per-target encrypted login bindings and journals; `WslCodexSwitchCoordinator` handles linked Windows/WSL progress, recovery and explicit abandonment.

## Authentication and data invariants

- Never read, print, log, copy, persist or transmit Claude authentication tokens. Official Claude Code owns sign-in, sign-out and refresh. Do not add a Claude token vault, OAuth implementation, proxy or global CLI shim.
- Preserve the original Claude home and its default global-config behavior. Additional profiles have separate official authentication; existing skills, projects and other working data stay in place. Never share the whole home or blindly copy account configuration. Preserve existing files if a link or registry is unsupported.
- The Claude Desktop account changes only through the official app (sign out and sign in). The utility never swaps logins, has no manual Claude "switch", and never starts an interactive Claude session with a utility profile; such a writer would be invisible to the app's own "in use" check.
- **In use** means the account the running Desktop app has confirmed in its current run: an initialization of a registered account/organization pair logged after the app's host process started. Sign-out, an unregistered account, a new app run or any gap in following the log invalidates it; a closed or uninspectable app has no current account. Identify the followed log file by its volume and file index from the reading handle, not its creation time (a new `main.log` inherits the renamed file's creation time on NTFS); an unreadable file, a rotation that cannot be bridged or a rotated file ending mid-line is a gap, and no account is confirmed from lines before a mid-line end. The widget follows the confirmed account by selecting its verified usage profile on the UI thread, and a selection that outlives its reason is discarded. A failed selection is retried after two minutes, or at once after that account's usage check or sign-in succeeds; a newer app account replaces a selection in flight, and only the current request may change the follow state. While the running app is signed out, on an unregistered or not yet confirmed account, or on an account other than the selected usage profile, show `—` with the reason, never another account's number. A lapse in observing the same run, or an app process that cannot be inspected, keeps what was shown; a closed app, or a new run not observed yet, shows the last selection. Shared settings and safe-mode usage must resolve to the same subscription identity. Never return an old profile/account observation under a new selection.
- Session lists: Desktop reads only `%APPDATA%\Claude\claude-code-sessions\<account>\<org>\local_*.json`; transcripts under the Claude home's `projects` are shared by every account. Fill other accounts' lists by adding records, or by advancing an older state of a conversation another account continued to its newest state in place (below). With Desktop and its Code CLIs fully closed every list is filled; an unknown process state is not closed. While Desktop runs, only the lists of mapped accounts it has not shown or signed in to for two minutes (`SettleWindow`) are filled, and only after the widget has followed its log for two minutes without a gap, an Unknown run state or a widget start: the app ends the Code sessions of the account it left some seconds after it shows the next one (observed 2026-11-01: sign-out 03:55:35, sign-in 03:56:20, the next list read 03:56:22, about 20 CLIs of the account left ended 03:56:28). The account shown stays shown while the app is signed out, on an unregistered account or in a state the log cannot tell, until it confirms another account or closes. The log tracker keeps the accounts left since the last confirmed one from the sign-in lines themselves (`ClaudeDesktopLogWatcher.Held`), so a widget started while the app is signed out, or a replay after a gap, still leaves them alone. Every organization of the account shown or signed in to counts as shown: a sign-in names the account before its organization, and a switch of organization inside one account may come with no sign-in line. A running fill comes every minute and at once when the app's account state changes (a sign-out fills the next account before the app reads it); it compares and writes only the lists it may write, writes no sidebar state, and leaves no ledger run when it wrote nothing. Re-plan immediately before publishing, check Desktop again before every file (while it runs, its process and log again for that file's list), and hold the lease that lifecycle scripts take. The plan that is published reads every record from its file. The plans in between, one a minute, may take a record whose file has the size and times of an earlier read from that read, but never one read within two seconds of the file's write time or more than ten to twenty minutes ago (spread by file name, so a list is not read whole again in one minute): the stamp does not name the content (two writes in one tick of the clock share a write time, and a file replaced under its name keeps the creation time; reproduced 2026-11-14). Where the published plan's lists differ from the plan before it, nothing is written and the next run starts from what was read then. After every 128 MB the process allocated, the background pass ends with one compacting collection: right after a pass that reads the lists whole (the first one, a published plan, a plan for the session sync), and some ten minutes apart otherwise. So little is allocated between such passes that the collector would otherwise leave their arrays with the process, a step higher each time. Right before each record is added, its original must still decide as planned (`DecisionFields`) and its transcript be there, so a conversation the user deletes or archives in the list the app shows is not shared meanwhile (the app removes a transcript no other list holds). Never delete a record, and never change one the app wrote except by that advance.
- A new record gets a fresh `local_<uuid>` app id and the source's current `cliSessionId`. It carries the display fields, a validated model and explicit effort, and the lineage ids (`priorCliSessionIds`, `rewindEdges`, `transcriptCuts`); the app protects transcripts from deletion per id. `adoptedFromOtherSurface` follows the source. Permissions, approvals, connectors, bridge/remote-control state, trust anchors and fork/spawn links are never copied.
- Skip archived sessions, sessions without a current transcript id, folderless scratch sessions (the app deletes their folder without checking other accounts), remote and Cowork sessions, sessions whose worktree is not made yet (`worktreeLazy`), sessions whose record carries `overflowCliSessionIds` (past 1,700 earlier transcripts the app keeps the oldest ids there and still counts them against a delete; a copy carries only `priorCliSessionIds`, so it would lose them; a record holding the field is not advanced either), and missing folders or transcripts. A session in a worktree is copied as the app's own import makes it: its folder (`cwd`, `originCwd`) without the worktree fields or branch, which stay with the account that made the worktree. A session a live CLI is writing is copied too: the record points at the transcript as it goes on, and the app shows one account at a time and ends the Code sessions of the account it leaves. Only `<pid>.json` files in the `sessions` registries of the Claude home and every utility profile are registrations; one is a writer while that process lives with a matching start time. A malformed registration of a live process, or a registry that cannot be read, holds every list; one of an exited process is ignored whatever its age. Hold a target list that has `.json.tmp` recovery files or unreadable records. A list whose record has not parsed for two minutes is reported in the account tab footer and the tray (`ClaudeShelfStatus.Damaged`): the app counts the transcripts of a record that does not parse only as far as a text scan still finds their ids, so one empty or cut short claims nothing, and until it reads again a delete of that conversation in another account may take its transcripts. Treat a `deleted_` marker or a ledger record the user removed as that account's decision, and never recreate it.
- Judge presence by conversation lineage, proven by the transcripts: a record whose current id another record lists in `priorCliSessionIds` is an older state of that conversation only when the other record's plain lineage begins with its own, the other is no fork or spawn, and the hand-over from its current transcript to the next is dated with nothing written to it afterwards (`WentOnFrom`; a CLI can resume a transcript under the same id, which makes it a branch). A line of nothing but NUL bytes in the earlier transcript is an entry the file lost and is passed over when dating the hand-over: it can only make the hand-over earlier, which keeps the record. Anywhere else, in its tail or in the later transcript, it stays a broken line. What cannot be proven is no. Never copy an older state, whether the source's own list or the target list holds the conversation further on. A copy this utility made whose current id a newer record (existing or being published) in the same list now lists as earlier is archived in place (`isArchived`), never deleted, only while the app has not continued that copy, only when the copy is such an older state of that record, and only while the two transcripts are as the plan stamped them. The archived copy replaces the bytes the plan read through the same last-moment check as an advance (the list still left alone, the copy and the transcripts unchanged). Records the app wrote are never archived.
- Advance in place instead of adding beside: when the record of a list holding the latest earlier state of an offered conversation (unique, unarchived) may be advanced, it is rewritten to the newest state, as the app does when a conversation goes on within one account. Offers are first grouped by that record across all source accounts; an offer that is an older state of another (as above) drops out, and only a single remaining newest state advances it, once per plan whatever the account order (two or more are branches and are added as before). The record must pass the source exclusions, be stored under its own id, be its list's newest state, and hold none of the import, other-transcript, session-kind or pending-work fields in `HoldingFields` (read from Claude 2.42304: confirming an import moves `stagedTranscriptPath` over the current transcript). "One line" means plain lineages (no id twice, no restored self-listing) where the newer starts with the older, the older rewind edges come first, in order and unchanged, every edge stays within its lineage, every older cut is kept, the folder is the same, the newer is no fork or spawn, and every hand-over from the older current transcript to the newest is dated as in the session plan with nothing written to the earlier transcript after it, the steps the newest state skips included (`Continues`). A record with worktree fields is not advanced: an advanced record keeps only `KeptFields`, and the account would lose the worktree the app made for it. A lineage waits (`live_writer`) while a transcript before a member's current one is written; the current (newest) one may be written meanwhile. The plan carries what the decision read: a hash of the source records' decision fields (`DecisionFields`: conversation, lineage, folder and kind; the activity times, title and turns the app keeps updating are taken as planned) and, stamped before reading, the size and times of each transcript from the older current one on (the newest by its creation time and a size it may only grow from). At the last moment before the swap these, the record's bytes and the writers of the earlier transcripts are checked again (a source record this run advanced itself counts as unchanged); any difference leaves the record for the next run (`advance_failed`), so a CLI that resumed a transcript and finished after the plan is not overwritten. The new record is `BuildRecord` of the newest state with the older record's id, the fields in `KeptFields` (its name, pin, folder and the choices the app's own fork carries) and the newest per-transcript models; everything else goes. Before the swap the ledger records the advance (`advanced`: from/to ids, before/after hashes) and saves the record as it was in `advanced\` beside it (the newest 50 kept); the next run confirms or cancels an interrupted one from the file. Advanced records are never added to `created`, and an advanced copy's ledger entry is left as it was, so retitling, retiring and undo leave it alone. A record advanced and then removed keeps both ids out of that list. The swap is atomic but not excluded against an app starting at that instant.
- A copy follows its original's title (`title`, `titleSource`) while it is still that original's copy: the same `cliSessionId`, not archived, not used in its own account after the original (`lastActivityAt`), and not renamed there since its title was last in step (the ledger's `title`). An older entry without a recorded title starts tracking once the copy shows the original's title; until then only a copy byte-identical to what was written is renamed. The app's `previousTitles` cannot prove a copy kept its name: it records neither a first name nor a change of case or spacing. The holds that apply to filling apply here (lists outside the run, held lists; a conversation being written is retitled all the same). Write only to a list the run may write (any while Desktop is closed, one it leaves alone while it runs), through a partial file, and only if the copy still holds the bytes the decision read; a failed write leaves the run unfinished. The ledger hash follows the new bytes only when the copy was untouched.
- Pins and groups are not carried across accounts. Desktop keeps them in web-UI state it owns: the settings file's `preferences.epitaxyPrefs` and the localStorage `LSS-persisted.*` keys are mirrors it rewrites on start; the zustand `dframe-store` in localStorage holds `pinnedOrder` and `customGroupsByScope`, but the app reconciles other accounts' groups on start; the Code list's starred pins persist in IndexedDB (`dframe-starred-code`). Live tests in October 2026 lost every write to the settings file and to localStorage. Chromium retries its LevelDB lock for about a second and may then destroy the database, so never write web storage while the app could start. Production passes no settings path; `ClaudeSidebarPrefs` and `ClaudeLocalStorage` remain for read-only diagnosis and tests. Do not re-enable without a source of truth the app keeps and a write the app's start cannot race. (Corrected 2026-10-12: the Code sidebar shows the IndexedDB list `store:pin-state:dframe-starred-code`, one list for every account; the user confirmed on screen that a session whose record says `isStarred: true` was not pinned. Records are a mirror: the app pushes the list into them on start, `true` only, and never clears a stale pin, and the session tools' `pinned` reports the record. The 10/07 check had compared two record-backed sources.)
- Session layouts across accounts: `session-layout.json` (version 2) in the shelf ledger folder keeps, per mapped account, its label, when the app last came to it (`arrivedAt`) and left it (`leftAt`), its stay count (`stay`, one more per arrival), a checkpoint of what its Code sidebar showed (groups by id and name in sidebar order; per session the pin, group name, title and, for the widget's copies, the title the ledger said it wrote; and per session nested then (`nested`), what it would show once out of its family: pinned where it or its family showed pinned, and the group it is filed under itself), the newest change it made to each value (`changed`: per session and field the value, when, and the account it came from when a plan brought it in; `groupsChanged`: its group list with its renamings, accumulated), the plan in progress there (`pending`: per session and field the target with the change it comes from, whether the plan files it into a group, the group list target and the groups it renamed out of the way by id), and evidence carried from version 1; plus the account last confirmed (`active`). Only the widget writes it, from its background pass: a process inside the Claude app (MSIX) that wrote the ledger folder could create a virtualized copy that hides the widget's file. A version 1 file (per-pair agreements) carries over its accounts and `leftAt`, and as evidence which sessions an agreement showed a pin or group for, so such a copy's no pin or no group counts as a value when it is first seeded. A file that is there but cannot be read is never replaced (`layout_unreadable`); with none, the widget starts it once the mapped accounts are known, taking the account the old `session-reference.json` names as left when it was chosen (an old reference that is there but cannot be read holds the start; a plan meanwhile says `widget_not_ready`). On a switch it watched (the app's confirmation after one it saw, with no lost log lines between) the widget dates leaving and arriving by the log line that confirmed the account; a switch it only finds later (the first confirmation after it starts, which it compares with `active`, or one after lost lines) dates the arrival only and leaves the account left as it was, since when that stay ended is unknown. It checkpoints an account it comes to, or sees without a checkpoint, as soon as everything reads whole (retried for two minutes). A checkpoint needs every record, the pins, the groups and the ledger readable; it dates what changed `now` when the previous checkpoint is of the same stay and `leftAt` otherwise (the minimum time when never left), seeds a first one with what the copy rule gives, settles the plan in progress (a value it reached counts as the change it came from, at that change's time and account; one not reached yet stays in progress; a pin its move into a group undid is taken as it shows and pinned again later; anything else is the account's own change), takes a group list holding a group the plan renamed out of the way (by id once that rename is done, or by the mark ` (옮기는 중` when not known) as mid-move and records no list change then, keeps the pins it had while the app's pin list, one for every account, is empty though a checkpoint showed pins (`PinsLost`; emptied by hand in every account it looks the same), forgets changes only of sessions whose record file is gone (archived ones keep theirs), and drops a plan of an earlier stay except groups still renamed out of the way. Plans: `WeeklyUsageIndicator.exe --claude-session-plan --session <local id> [--only <account/org>] [--settle <seconds>]` runs before the single-instance claim. Without `--only` it asks the running widget through named kernel objects (files the command wrote under the local app data could be virtualized): under a per-account mutex it writes `{id, self}` into the widget's shared memory, sets `Local\CodexWeeklyUsageIndicator.SessionsPlanned.<account>_<org>` and waits up to 30 s for `...SessionsCheckpointed...` with an answer carrying the same id (an earlier request's late answer is passed over). The widget answers after its log pass: for the account the app shows it reads everything once, checkpoints from that read, makes the plan from the same read and that in-memory layout, keeps the plan's targets, saves, and returns the plan with `checkpointed: true`; otherwise, or when it cannot save, a plan with `checkpointed: false`. Without an answer the command makes the plan itself, also `checkpointed: false`, for viewing only; the skill applies only checkpointed plans. A plan reads titles from each account's session records, pins from the IndexedDB pin list (`ClaudeSidebarPins`; records' `isStarred` is never read), groups from `dframe-store` `state.customGroupsByScope` in the order and folding of `state.codeSidebarByScope[scope].sections` (a manual section's id is its group's; groups it does not place follow in stored order; an unfamiliar shape is unreadable). Per conversation and field the newest change wins among this account's (with what changed since its checkpoint, newest of all when that checkpoint is of this stay) and each other account's (with what changed since its checkpoint, dated its `leftAt`), each classified against that account's plan in progress, its older states included, archived ones too, each found again as an older state of that conversation in every plan (an archived branch never counts for another conversation), except that a pin or group taken off an older state after the conversation moved on only put that line away; a tie goes to this account, then the account left last; with no change a value stays. The copy rule: a record of the account's own gives everything; the widget's copy (its ledger) gives a group only when filed, a pin when pinned or filed (filing unpins, so its pin was chosen since), and a title once it differs from the title the ledger says the widget wrote (where untracked, once renamed per `previousTitles`); a copy's title that changed to a newly written one since the checkpoint was the widget's, not a choice. The group list follows the newest change, lists mid-move skipped, plus any group this stay filed a session under; renamings from every account resolve chains. A session whose target group the list lacks follows the renaming to a listed name or leaves for no group; a group this stay filed a session under by hand stays in the list. Alignment keeps the longest start of the target list that the groups already show in order, renames each group out of place or going to `<name> (옮기는 중)` (numbered on a clash), creates the rest at the end in order (the app appends new groups, returns the existing group for a duplicate name and has no reorder tool), moves sessions by group id where the group stays and by name where it is made, and deletes groups the moves empty of every session a list shows (a delete waits for `session_count` to fall to `hidden`); the archived sessions filed under a group made anew or one the list lacks leave it (`hidden`), as the app moves no archived session (Claude 4.23118 refuses the whole move). Older states in a group made again or going follow. Unreadable pins plan neither pins nor groups (a move unpins); a lost pin list plans pins back from the newest changes (`pins_lost`); another account's group scope that is missing gives no groups, one that is there but unreadable holds every group change (`groups_unreadable`); a ledger that is there but cannot be read whole (`ledger_unreadable`) or any list that cannot be read whole (`list_incomplete`) plans no pins, groups or titles; a group assignment the scope does not list moves nothing (`groups_unresolved`). A session the app nests under another shows the group of the session at the top of its family and moves only with it (read as its sidebar does, Claude 3.1623: by the record's lineage unless `lineageDetached` — a side session Claude started under its starter, else the session it was forked from, else the one whose suggestion started it — when that parent is in the list and live, or archived along with it; a live one under an archived parent sits under the nearest live session above it; a family climbs to its top). The app refuses a move naming it without that session ("nested sessions move with their parent. Nothing was moved.") and drops its own assignment when both move together, so its own assignment counts for nothing (shown, checkpointed and emptied as the top's), it is never moved, no group change is recorded for it (one recorded earlier is dropped at the next checkpoint), and another account takes for it only what its own account did to the top session's group (a group a plan brought to the top session there was another account's change to a session of its own). When the user moves one out of its family (`lineageDetached`), the app pins it where its family showed pinned, and it shows the group it is filed under itself or, where the app dropped that as its family moved, none; neither is anyone's change: a session its checkpoint saw nested that is out of its family now records no change to pinned where the checkpoint foresaw that and its family (the top above the lineage link it had, read even once detached, climbing archived sessions as the app nests) shows pinned now, and no group change to the group it is filed under (any, when that was unknown) or to none where its family's group changed since (a checkpoint an earlier widget took foresaw nothing; there a record detached and written since records no change to pinned where its family shows pinned, and no group change). Where these cannot tell the app's doing from the user's (the family pinned or unpinned since, moved away and back, or not known), it is the user's: a pin or ungrouping the user made must not be undone. Its group then follows the newest change made to it; a move of its family it went along with is not carried over. The widget's copies carry no lineage, so elsewhere the conversation is a session of its own. Conversations match per other account by current transcript id, else as a continuation either way. An older state is a record whose current transcript another record of the same list lists as earlier (not mutually, the lister no fork or spawn) and that has no entry after the conversation went on. It went on in the transcript every continuing record lists right after this one, which must also be the first created after it, at that transcript's oldest entry whose `uuid` this one does not hold: a continuation starts with copies of the earlier entries, ids and times kept (reviewed 2026-10-12 on nine real hand-overs: that entry is within half a second of the file's creation). The file must have been created by then (2 s slack), or it was restored and proves nothing. One written to afterwards is a branch and stays, as does the calling session. Every transcript of the record, of the continuing lineage and of the newest state must be present and dated, or the record stays; a file created after it was last written was copied. Only each line's top-level `uuid` and `timestamp` count. Record `createdAt` is per conversation and `lastActivityAt` moves without messages, so neither dates anything. This account's older states are listed for archiving; another account's are seen through. An older state is `ready` only when pins and groups are readable, its group and the newest state's resolve, and the newest state already holds the pin and group it should with no move or pin planned for it, so stopping part way never loses a pin or group; an older state's pin, undone by its move or before archiving, is in the plan's targets as nobody's choice. The plan also lists every account's sidebar by title in sidebar order with folding (pinned sessions only under Pinned, a nested session in its family's group, and the nested sessions with the title each is under), the conversations only this account lists, and per other account how many it shares and those only it lists; `--settle <seconds>` waits before asking so a check after applying sees the app's writes. The Claude-only `claude-session-sync` skill applies a checkpointed plan with the app's own tools in a fixed order (rename groups aside, create, move — a move into a group unpins — pin, rename sessions, delete the emptied groups), re-plans to confirm, then archives ready older states with the app's archive tool (unpinning just before) without asking, since invoking the skill is the consent, and archives here conversations archived in another account after their last activity, and shows the sidebars side by side. Sessions are never deleted, and the widget never writes the sidebar.
- The fill ledger (`%LOCALAPPDATA%\CodexWeeklyUsageIndicator.SessionShelf`) records intent before publishing and keeps only files whose content matches. Creation history is retained indefinitely; runs are capped. Undo removes only records the app never changed.
- Reopen Desktop only when the user asked on the account page. The first fill pass of the next closure consumes the request whether or not the reopen succeeds; a cancelled or replaced request is never used, an app that is already running again is not launched, and a request expires after 30 minutes, including while a pass runs.
- Map a profile to its account/organization only from the non-secret `oauthAccount` fields of the official global config, and only when they hash to the stored identity. Conflicting sections stay unresolved. Cache the mapping by profile, identity and config path. Removed profiles leave the cache.
- Before writing, the installed package must contain every compatibility marker, the stores and log lines the widget follows (`ClaudeDesktopProbe.Contract`); otherwise pause writes and say so (`Incompatible`). A package whose connected windows and data flows, the deletion protection below, read differently from the reviewed ones is `Unreviewed`: filling goes on, and the account tab footer and a tray message (once per version) ask the user to archive sessions rather than delete them until it is reviewed. The flows check, allowing renamed minified variables, that each record's current and earlier transcript ids enter the claims set, that the walk behind that set takes every account's folder and tells the current account apart only to skip records it holds in memory, that a session delete releases only unclaimed ids and asks the reap decision, which refuses claimed ids and fails closed on records it cannot read from disk, and that transcripts are removed only when that decision allows it, with nothing reassigning it and a failed check only logging and keeping. A name shared between flows stands for one function only while the file that exports it sets that export exactly once, by assignment, and the calling file binds the import to one required file and never assigns to the member. A delete owed to Remote Control sets transcripts aside under those same checks, keeps all of them when one refuses or fails, and removes them only after checking again, putting them back otherwise. What a guard's keep call returns is not checked. This guards against drift, not against every change of meaning. Re-verify the design when a check fails. While the app runs, an incompatible version is reported at once (footer and tray), so nothing promises a fill that will not run. - Processes started inside a packaged app (for example an agent shell) may have new `%LOCALAPPDATA%` files redirected to that app's private LocalCache. Run lifecycle scripts and live checks from an ordinary Windows session.
- Codex login replacement requires explicit user selection and stopped writers. Keep current live credentials authoritative during recovery; do not overwrite newer or different authentication with an old snapshot.
- Discover only running WSL distributions on an explicit environment check. Require an installed native Linux CLI, identified Linux user/home and supported file-based auth. Never force-install a missing CLI or rewrite unsupported managed/keyring settings.

## Usage and presentation invariants

- Do not add telemetry or direct provider usage network calls. Do not commit absolute local paths, real-account screenshots, pet assets, build output or credentials.

- Actual Claude usage calls must remain at least ten minutes apart per verified account, including manual refreshes, failures and cancellations. Different accounts have independent intervals; profiles with the same verified identity share request spacing and transient backoff. Metric selection reuses the snapshot. ## Install lifecycle

- Launch `--supervise` through the per-user interactive, least-privilege scheduled task, never directly from Codex. The supervisor retries abnormal exits/start failures only; normal Close ends supervision. Do not replace this loop with Task Scheduler RestartOnFailure.
- Disable/stop the task before upgrade or uninstall; filter processes by the current user's exact installed EXE path. Coordinate lifecycle scripts with in-progress account operations.
- Check the install directory's final handle path before stopping tasks or processes: packaged shells can redirect AppData without reporting package identity. Package `install-environment.ps1` with both lifecycle scripts.
- From a shell inside a packaged app, install with `.\scripts\install-outside.ps1`: it runs `install.ps1` through a one-off scheduled task of the current user, with no window, waits for it and compares the installed hash with the built one.
