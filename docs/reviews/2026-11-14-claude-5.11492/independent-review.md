# 독립 검토 결과

두 변경 모두 그대로 승인하기 어렵다. **대상 1은 현재 번들에 대한 보존 보장이 성립하지 않는 사례와 잘못된 `Reviewed` 판정 입력을 확인했다. 대상 2는 실제 NTFS에서 캐시가 변경을 놓쳐 중복 기록을 쓰는 사례를 재현했다.** 실제 사용자 대화가 이미 손실됐다는 뜻은 아니다.

각 작업 사본의 `AGENTS.md`, 기준 `bff4f51` 대비 `b5a096b`·`c44ee61` 변경, 설치된 Claude **5.11492.5.0**의 `app.asar`를 직접 확인했다. 아래 `contract/`·`memory/`는 각각 지정된 작업 사본이며, 오프셋은 해당 ASAR의 **10진수 절대 바이트 위치**다. 기존 코드의 문제와 이번 변경이 만든 문제를 구분했다.

## 대상 1 — a~e 판정

- **a. 예 — 정상적으로 읽힌 지원 형식의 로컬 기록에 한함.** 현재·unarchived id와 `priorCliSessionIds`·`overflowCliSessionIds`가 점유 집합에 들어간다. `14239276`; 메모리 계보 `14723884`. 손상 기록은 c의 예외가 있다.
- **b. 예.** 모든 계정·조직을 순회하며, `skipOwnRecordsOf`는 현재 계정·조직에만 적용한다. 실제 점유 조회는 `currentOrgOnly`를 전달하지 않는다. `14237185`, `14237608`, `15391340`.
- **c. 아니오.** 정상 점유와 I/O 실패는 거절하지만, JSON 파싱 실패는 부분 복구로 바꾸어 계속한다. 비어 있거나 현재 id 앞에서 잘린 다른 계정 기록은 그 id를 놓치고 삭제를 허용할 수 있다. `DB 14233142`, `NB 14238900` 이후 catch, `BX 14732623`.
- **d. 예 — 일반 세션 삭제 함수 `Ze` 내부의 연결에 한함.** 판단값을 false로 시작해 `reapIf` 결과만 대입하며, 예외·false이면 파일 삭제에 도달하지 않는다. `27696004`, `27696515`, `27697314`. 앱의 모든 파일 조작에 적용되는 보장은 아니다.
- **e. 예 — Remote Control의 두 단계 검사 연결에 한함.** set-aside 중 하나라도 거절·실패하면 앞서 옮긴 것들도 복원하고, finish는 다시 확인하며 검사 예외를 보존으로 처리한다. `27691895`, `27693518`, `14734075`. c의 불완전한 점유 판정은 그대로 물려받는다. 복원 실패 시에는 별도 이름의 파일이 남을 수 있으며, finish의 판정은 파일별이다.

### 작성자가 미확인한 두 가지

1. **워크트리 이전이 4.x에도 있었는지는 증명 못 함.** 확인 가능한 설치본은 5.11492.5.0이었고 4.x 원본을 열지 못했다. 테스트에 남은 옛 삭제 스니펫은 이 이전 동작의 증거가 아니다.
   - 현재 `hT`에는 세 모드가 있다. `exclusive`는 기존 대상을 우선하고 복사 뒤 원본을 지운다. `exclusive-live-writer`는 기존 대상을 우선하며 원본도 남긴다. **`shared-cli-project`는 기존 대상을 덮을 수 있지만 원본은 남긴다.** 따라서 “덮는 모드도 복사 뒤 원본 삭제”라는 설명은 정확하지 않다. 모드 `13674545`, 복사 `13676187`, 원본 unlink 조건 `13677196`.
   - **다른 계정이 사용하는 대상 파일의 내용 손실은 가능하다.** resume bring-home은 같은 id의 원본이 대상보다 크다는 조건으로 `shared-cli-project` 복사를 실행한다. 두 파일의 내용·공통 접두부·최신성·다른 계정 점유를 대조하지 않는다(`13784484`). 원본 20KB와 대상 10KB가 서로 다른 후속 내용을 갖는 상태라면 대상의 고유 내용이 덮인다. 조건부 실패 사슬이며, 실제 사용자 파일에서 이런 분기를 관측한 것은 아니다.
   - **원본 경로가 없어졌다는 사실만으로 다른 계정 기록이 영구히 끊긴다고 볼 수는 없다.** resolver가 cwd/worktree/origin을 시도한 뒤 모든 프로젝트 폴더에서 id로 다시 찾는다(`27668966`, `27672488`). 다만 같은 id의 파일이 여럿이면 일반 탐색은 큰 파일을 고르므로(`27673428`), 분기된 내용까지 안전하게 합쳐 준다는 보장은 없다.
2. **`deletingSessionIds` 때문에 다른 계정의 점유가 풀리지는 않는다.** 건너뛰기 조건에는 현재 계정·조직이라는 조건이 붙는다. 다른 계정은 파일명이 같아도 계속 읽는다. 삭제 중 id는 `midDeleteReleaseClaims`로 다른 삭제에 답하고, 자기 삭제에서만 자기 점유를 제외한다. skip `15391340`, 메모리 점유 `14725610`, 삭제 표시·점유 보관 `15269640`. 이 추가에 대한 작성자 결론은 맞다.

### 보호를 거치지 않는 경로

**있다. “보호 없이 지우거나 덮는 경로가 없다”는 앱 전체 주장은 틀리다.**

- 위 `hT` 이동·덮어쓰기에는 `reapIf`나 다른 계정 점유 검사가 없다. exclusive의 원본 삭제와 shared의 대상 덮어쓰기는 구분해야 한다.
- `confirmImportedSessionResume`은 staging 파일을 현재 id의 대상 경로로 rename하고, fallback에서는 대상을 지운 뒤 복사한다(`15389014`, `15389143`). 보호 검사는 없다. 다만 정상 가져오기는 새 UUID를 만들므로(`27888718`), 이 경로만으로 기존 공유 대화와 충돌한다고 입증하지는 못했다.
- fork의 새 UUID 파일 복사·실패 정리도 있다(`13861965`, `13862368`). 새로 만든 파일의 정리이므로 그 자체를 다른 계정의 데이터 손실로 판정하지 않았다. 번들 내 SDK의 무보호 `deleteSession`(`7096686`)도 발견했지만 Desktop 호출 경로는 확인하지 못했다.

## 대상 1 검사 코드 — P0

### P0-1. 손상 기록을 읽지 못해도 현재 번들이 삭제를 허용한다

**위치:** `contract/src/ClaudeDesktopProbe.cs:98`, `:118`, `:229`; 테스트 `tests/WeeklyUsageIndicator.Tests/ClaudeSessionShelfTests.cs:577`의 `CollectIds5`.

계정 A의 대화 id가 X, 위젯이 만든 계정 B의 기록명이 `local_Y.json`이라고 하자. B 기록이 비거나 `cliSessionId` 앞에서 잘리면 `NB`는 파싱 오류를 `DB`의 문자열 복구로 넘긴다. `DB`는 id를 하나도 복구하지 못해도 정상 반환한다. 점유 집합에는 파일명에서 얻은 Y만 남고 X는 없다. 다른 거절 사유가 없는 상태에서 A를 삭제하면 `BX`는 X 삭제를 허용한다. I/O 오류 때 `null`로 닫히는 것과 다르다. 앱에는 직접 덮어쓰기 fallback도 있으므로 손상 기록을 지원 범위 밖의 가정으로 치울 수 없다.

번들의 `DB`·`NB`·`BX`를 메모리 파일시스템에 연결한 재현에서 **정상 B 기록은 `reapAllowed=false`, I/O 실패도 false, 빈 기록·id 앞에서 잘린 기록은 true**였다. 설치 ASAR 자체는 수정된 `Contract`에서 **Reviewed**였다. 정규식은 `null`의 소비와 정상 id 루프만 확인하고 복구의 완전성을 확인하지 않는다. `CollectIds5`는 실제 파싱 실패 처리를 `catch(a){}`로 축약해 이 실패를 시험하지 않는다. **5판에서 처음 생긴 문제라고 입증한 것은 아니며, 이번 보존 보장 재검토에서 놓친 문제다.**

### P0-2. 위젯이 `overflowCliSessionIds`를 버려 정상 기록의 과거 대화가 보호되지 않는다

**위치:** `contract/src/ClaudeSessionShelf.cs:134`, `:1021`, `:1040`; 이를 포함한 현재 조합을 Reviewed로 판정하는 `contract/src/ClaudeDesktopProbe.cs:229`.

앱은 오래된 prior id를 `overflowCliSessionIds`로 넘기고(`14455782`), 점유·삭제 대상에 그 필드를 포함한다(`14239276`, `14723884`). 그러나 `BuildRecord`의 `LineageFields`에는 이 필드가 없다. **A={current X, prior P, overflow O}를 B로 채우면 B에는 O가 없다. A 삭제 시 O를 지킬 다른 점유가 없어 O의 대화 파일을 삭제할 수 있다.** 실제 `BuildRecord` 호출에서 prior는 복사되고 overflow는 빠졌으며, 번들의 점유·판정 함수에서도 O에 대한 삭제 허용을 재현했다.

이것은 **이번 커밋이 새로 만든 복사 버그는 아니다.** 하지만 5판의 완전한 계보를 확인하고도 현 위젯과의 조합을 안전하다고 승인할 수 없게 하는 구체적 누락이다. 앱의 수집 루프가 맞는지만 시험해서는 위젯이 만든 기록의 보존까지 증명되지 않는다.

### P0-3. 새 파일 간 이름 풀이가 뒤의 export 재대입을 무시한다

**위치:** `contract/src/ClaudeDesktopProbe.cs:304`—특히 `:312`, `:324`—및 `tests/WeeklyUsageIndicator.Tests/ClaudeSessionShelfTests.cs:774`.

`Function`은 `require`의 파일명과 처음 발견한 `exports.f=Ze`로 연결을 확정한다. 그 뒤 같은 export가 바뀌어도 검사한 함수와 실제 호출 함수가 같다고 판단한다. 기존 `Bundle5()`의 `exports.f=Ze`를 다음 문자열로 바꾼 **구체적 입력도 Reviewed**였다.

```javascript
exports.f=Ze, exports.f=async(e,n)=>{
  for(let id of n) await require("fs").promises.rm(
    await e.resolveProjectDirForSession(id)+"/"+id+".jsonl", {force:true});
}
```

보호된 `Ze`는 남아 있어 모든 흐름 검사를 만족하지만, 실제 `Gt.f`는 검사를 생략하고 파일을 지운다. 호출 직전 `Gt.f`를 같은 함수로 바꾸는 입력도 Reviewed였다. **설치 앱에서 이런 재대입을 발견한 것은 아니며, 새 검사 코드의 허용 구멍을 재현한 것이다.** 기존 변이 시험은 `exports.f=Ze`를 `exports.f=Qe`로 단순 치환하는 경우만 막으며, 나중 재대입은 막지 못한다.

### 그 밖의 메모

- 마커 누락은 계속 `Incompatible`이다. 다만 흐름 불일치는 규칙대로 `Unreviewed`이며 **쓰기를 중단하지 않는다**(`ClaudeDesktopProbe.cs:223`–`:229`, `AGENTS.md:32`). 따라서 이 검사를 전반적인 “쓰기 fail-closed”라고 표현하면 안 된다.
- 실제 설치본의 `require`→export→삭제 함수 연결, `reapAfter`, `currentOrgOnly`의 용도 분리는 확인했다. 해당 변이 시험들은 통과했고, 작성자의 이 부분 설명을 틀렸다고 볼 근거는 없다.

## 대상 2 — P0

### P0-4. NTFS에서 같은 메타데이터의 다른 파일을 캐시로 읽어 두 계획과 최종 쓰기가 모두 통과한다

**위치:** `memory/src/ClaudeSessionShelf.cs:1132`–`:1136`(캐시), `:85`(비교), `:874`–`:883`(두 계획), `:823`–`:830`·`:908`(추가 직전 확인).

크기·생성 시각·수정 시각은 파일 내용의 식별자가 아니다. 앱은 평소 `writeSessionToDisk`에서 **`.tmp` 작성→sync→close→rename**하고, 일부 오류에서는 제자리 쓰기로 fallback한다(ASAR `15186229`, `18389469`, `18396902`, `18390930`). 읽는 핸들에서 시각을 얻어도, 다른 내용이 같은 튜플을 갖는 경우는 구분하지 못한다. NTFS의 [100ns 시각 단위](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/4e3695bd-7574-4f24-a223-b4679c065b63)는 내용별 고유성을 뜻하지 않는다.

**실제 C: NTFS, 합성 계정·기록만으로 다음을 재현했다. 시각 설정 API는 사용하지 않았다.**

1. A는 대화 X, B는 대화 Y를 가진 상태를 캐시했다. B의 현재 id를 같은 길이인 X로 바꾼 기록을 임시 파일에 쓰고 `Flush(true)`·close·원자 교체했다.
2. 반복 중 8,198번째에 이전·이후 핸들의 튜플이 자연스럽게 일치했다: `(355, 639302361667519744, 639302362647623358)`.
3. 이후 두 계획은 모두 B가 아직 Y라고 읽어 `SameShelvesAs=True`였다. 새 shelf 인스턴스가 실제 파일을 읽은 계획과는 달랐다. **캐시 계획의 추가 2건 / 새로 읽은 계획의 추가 0건**이었다.
4. `Apply`의 마지막 확인은 A 원본과 X 대화 파일만 새로 확인한다. B에 X가 이미 있다는 사실은 다시 읽지 않는다. **`Created=1`, B에서 현재 id가 X인 기록 2개**가 됐다.

따라서 “매 쓰기 직전 새로 읽으므로 캐시는 잘못된 쓰기로 이어질 수 없다”는 주장은 틀리다. 대화 파일 손실까지 재현한 것은 아니지만, 이미 있는 대화를 추가하는 잘못된 쓰기와 재계획 불변 조건 위반은 재현했다. 이후 시각이 바뀌지 않으면 두 분의 안정 대기도 이 낡은 캐시를 고치지 못한다. 발행에 사용하는 대상 목록·존재 판정은 캐시와 독립적으로 검증해야 한다. 기존 `TestScansFollowChangedRecords`(`tests/WeeklyUsageIndicator.Tests/ClaudeSessionShelfTests.cs:100`)는 크기 변경 또는 mtime 1초 증가만 시험한다.

### 그 밖의 메모

- **개별 기존 기록의 덮어쓰기 보호는 유지된다.** `Replace:811`, `Archived:839`, `AdvanceInPlace:1008`, `Unchanged:354`는 바이트/판정 필드를 새로 확인한다. 제목도 후보 선택 뒤 원본·복사본을 다시 읽고 판정한다(`FollowTitles:710`–`:728`). 위 P0는 새 기록을 추가할 때의 **대상 목록 존재 판정**이다.
- **공유 객체 오염·스레드 안전성:** 현재 호출 경로에서 구체적 결함을 찾지 못했다. 캐시 사전 접근은 잠그고, `BuildRecord`·advance는 노드를 복제한다. 서비스는 `_busy`로 백그라운드 패스를 직렬화한다(`ClaudeShelfService.cs:148`). 계획 명령 응답은 같은 Work의 `ServePlans:451`에서 별도 `ClaudeSessionSync.Serve`를 사용하며 이 shelf 캐시를 공유하지 않는다.
- **캐시 잔류:** 현재 스캔한 기존 디렉터리의 사라진 파일만 제거한다(`ScanShelf:1094`, `:1112`). 프로필이 제외되거나 디렉터리 자체가 없어지면 그 항목은 남는다. 계정·경로가 계속 교체되는 환경에는 상한 없는 누적 경로가 있다. 고정된 세 계정에서 곧바로 무한 증가한다는 뜻은 아니다.
- **실패·복구:** 실제로 읽은 파싱 실패는 캐시하지 않고 대상 목록을 보류한다. I/O 실패는 패스를 중단한다. `.json.tmp`는 매번 새로 해시하고 대상 목록을 보류한다(`:1099`, `:229`). 같은 튜플의 낡은 캐시가 먼저 반환하는 경우는 위 P0의 예외다.
- **흘려 읽기:** 이전 구현과 실제 메서드를 대조한 **327개 사례에서 차이 0건**이었다. NUL 전용 줄의 earlier 쪽 예외, 나머지 깨진 줄, CRLF, 버퍼보다 긴 줄, 개행 없는 마지막 줄, 512MiB 초과 거절을 포함했다. `ClaudeSessionSync.cs:2242`–`:2283`의 상한·열 때의 길이 고정도 이전 의미를 유지한다. 단일 거대 줄은 그 줄 크기만큼 버퍼가 커질 수 있으므로 항상 작은 고정 메모리라는 뜻은 아니다.
- 2시간 이상의 private 메모리 추이는 측정하지 않았다. 반복 전체 읽기의 감소는 코드로 확인했지만 3.4GB 현상의 해소까지 검증한 것은 아니다.
